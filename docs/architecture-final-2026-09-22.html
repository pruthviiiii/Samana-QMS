Samana QMS: final production architecture

22 September 2026 · Third and final report of the day · Code at commit 9295489 · Written for management, engineering, and whoever reviews this next

The system now has the architecture the external review asked for, built properly rather than bolted on. The API is its own service, unreachable from the internet. The web tier serves screens and holds no credential of any kind. Prisma is the master description of the data and the typed client for every record, and the queue engine's rules stay in PostgreSQL behind typed, validated calls. Every one of those statements is enforced by a test, not by a convention.

Two of the review's prescriptions were declined a second time, on evidence: rewriting the queue rules in application code, and using Prisma to run migrations. Section 5 gives the reasons and what each would cost. The rest of the review's document is now satisfied line by line, and the one part of §03 that was a genuine code fault, results asserted rather than checked, is closed.

4. The defect the new tests found

This is the part of the round most worth a reader's attention, because it is the argument for the data-layer tests in one paragraph. When the Prisma client was first wired in, a new test inserted a session that had expired one second earlier and asked the client for it. The client returned it. Investigation showed that on a database whose session time zone is Asia/Dubai, as the company server's is, the client read every timestamptz four hours late and sent every Date parameter four hours early. Sessions would have stayed valid four hours past expiry, the two-minute lookup reuse window would have been wrong, and every time in the activity log would have shown four hours late. The raw pg path was unaffected, which is why nothing earlier had caught it.

The fix is the correct one rather than a patch: every pooled connection now sets its time zone to UTC, which is what the Prisma client assumes and what the raw queries never depended on, because every calendar-day rule in the SQL names Asia/Dubai explicitly. A probe run through the same client before and after shows the read-back timestamp moving from four hours off to identical, and the expired session moving from found to not found. A regression test asserts the session time zone is UTC and that a timestamp read through the client equals the same timestamp read raw.

5. Kept by decision, and why

DecisionWhat the reviewer wantedWhy it stands
The queue rules stay in PostgreSQL functionsBusiness logic in TypeScript, reached through PrismaIssuing a ticket numbers it, inserts it, routes it and raises the change notification as one indivisible step, and calling a customer must guarantee no two agents hold the same ticket. Those guarantees come from one advisory lock and a partial unique index inside the database. Rebuilt in application code they would need interactive transactions with row locks in every path that touches the queue, five to ten round trips per action instead of one, and the lock held several times longer, which is the opposite of what §07 asked for. Three to four weeks and a downgrade in both safety and throughput. The rules are now reached through typed wrappers with validated results, which is the part of the complaint that was about code quality rather than location.
Migrations stay as checksummed SQL filesPrisma MigratePrisma's schema language cannot express the functions, triggers or the partial indexes the engine depends on, so Prisma Migrate would describe less than the SQL does and generate migrations that omit the engine. Prisma describes the result of the migrations instead, and a test proves the description matches. Nothing the reviewer complained about in §04 (rewritten rules, no checksums, untested parser) depends on which tool applies the files; all three are closed.
Web and API in one repositoryIndependent deploy schedulesThey are separate services with separate build commands and separate images; either can be redeployed alone. A second repository would add a shared-types package and a release coordination problem for one developer and one product. The extraction into another repository is mechanical if a second team arrives.
Three stylesheets, app shell at about 1,000 linesOne styling system, smaller componentsUnchanged this round and stated as such. The provably dead blocks were removed this morning; the remaining overlaps change what customers see and are a design decision.

7. Deploying it

Render. The Blueprint now declares three services. An existing deployment must sync the Blueprint once after this commit reaches main: Render creates the private API service, asks for the secrets once (they move from the web service to the API), and wires the API's private address into the web tier. Between the deploy of the web tier and that sync, the web tier answers every API call with 503 API_NOT_CONFIGURED, so sync straight after the push. The steps are in docs/render.md.

Your own server. docker compose up -d builds the three images and starts them on one private network; only the web tier publishes a port, on the loopback address, for a TLS reverse proxy to front. The API never needs a public address.

Any Node host. Three processes from three artefacts: node dist-api/api.mjs, node dist-node/standalone/server.js with API_URL pointing at the first, and node dist-worker/worker.mjs.
