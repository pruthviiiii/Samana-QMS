Samana QMS: architecture review, and what was changed

22 September 2026 · Second review, read as an enterprise architect · Code at commit 7486861 · Written for management, engineering, and whoever reviews this next

Verdict: production-ready, and now defensible line by line. This is a stricter pass than the external review of 21 September. It read every server module, the data hooks, the workspace shell, the schema and the tests, and judged them against enterprise practice rather than against the earlier review's list. It found 15 things worth changing in the application and 2 in the Salesforce client. All 17 are done, each with a test or a measured proof, and the decisions kept on purpose are defended below with their cost of reversal.

For the next reviewer: every claim in this document is reproducible with the commands in section 6, on any PostgreSQL 14 or newer server, with no external secret.

2. Findings, and what was done about each

Severity is as judged before the change. "Proof" names the test that now fails if the fix regresses, or the measurement taken.

#FindingSeverityWhat changedProof
1No validated configuration boundary. Eighteen files read the environment directly; nothing checked it at start, so a missing QR secret first appeared as a 503 in front of a customer and a misspelled cookie flag silently changed behaviour.HighOne module reads and validates every setting once and freezes it. The web server and the scheduler call it before serving anything; a bad deployment stops at boot with a message naming the variable. Empty strings mean unset, as hosting dashboards express it. Contradictions are refused: SMS on without a gateway, write-back on without a connection, a Secure cookie on an http:// origin (browsers would drop it and nobody could sign in), an insecure cookie on https://. A test pins that only four files may touch the environment, each for a stated reason.tests/config.test.ts (16 cases); tests/boundary.test.ts "reads the environment in one place"
2Content Security Policy allowed inline scripts. For a system holding Emirates ID and passport numbers, 'unsafe-inline' removed most of the protection the policy exists to give.HighA nonce is minted per request; the policy allows scripts only by that nonce with 'strict-dynamic', and the renderer stamps it on its bootstrap script. Every page now renders per request, because a page prerendered at build time would carry a stale nonce. Inline styles remain allowed: a style cannot execute code, and the design system sets them.Built server, real browser: 15 script tags, 15 carrying the nonce, 0 without; login form hydrated; 0 policy violations. tests/proxy.test.ts (6 cases)
3Three hot queries had no index. Unread notifications on every queue refresh, the outbox claim every 15 seconds, the lookup reuse check on every check-in: all planned as sequential scans.HighMigration 016 adds a partial index on unread notifications by user, an index on outbox readiness, one on lookups by identifier and time, and one on audit events by action. Applied to both local databases and, on deploy, to production.db/016_hot_path_indexes_and_limits.sql; schema snapshot test
4Routing and delivery shared one loop. A slow Salesforce delayed presence expiry and five-minute re-routing by however long deliveries took.MediumThe scheduler runs two independent, non-overlapping timers: routing every 15 seconds, delivery and retention on their own cadence. It also drains the pool on shutdown.scripts/worker-entry.ts; smoke test ticks
5The rate limiter had a window race. Two simultaneous first attempts each saw no live window and opened their own, briefly doubling the budget.MediumOne row per key; the whole decision is a single upsert with the window reset inside the statement. The migration changes the primary key and clears the transient counters.tests/security.test.ts (4 limiter cases)
6Unknown errors returned 503, telling monitors and load balancers the service was down when one request failed.MediumUnexpected faults are 500 with a request id and a stable code; 503 is reserved for a dependency that is genuinely unavailable.tests/api.test.ts "keeps provider errors distinct from no match"
7Errors were mapped by substring. A database message containing FORBIDDEN, or a Salesforce message containing (404), decided the HTTP status.MediumError identity is a field. Database rules map by SQLSTATE P0001 and the exact rule name; the Salesforce client carries the org's status on a typed error; the browser client exposes a typed error with status and code. Rewording a message can no longer change a status.lib/errors.ts; every existing API test passes on the new mapping
8Role lists were duplicated in the browser, the defect the first review raised, surviving on the client.MediumFour role groups are defined once in the domain module. The route table declares access with them and the workspace decides what to show with them; there is no second list.lib/domain.ts; no role array remains in components
9Navigation bypassed the framework router with a hand-rolled history listener.MediumThe address is the view. Next.js keeps the two in step, including back and forward.components/qms/app.tsx
10Refs were mutated during render in both data hooks.MediumMirrors are written in effects, so a render React discards leaves nothing behind.use-queue.ts, use-live.ts
11Dead business rules. Two TypeScript rules were tested and exported but called by nothing, because the real rules live in SQL.MediumDeleted, with their tests. The database functions are the one definition and 29 workflow tests exercise them.lib/domain.ts
12No graceful shutdown.LowOn SIGTERM the web server closes the pool and the change listener; the scheduler finishes its tick and closes the pool.lib/lifecycle.ts, scripts/worker-entry.ts
13Scanning the check-in link on a TV signed the TV out.LowA display session is kept; the request is refused with a message to scan with a phone.lib/public-access.ts
14The application role may execute every function.LowKept, with the reason in section 4.—
15No coverage metric, no component tests, order-dependent API tests.MediumA second test project runs component tests in a DOM for the check-in screen and the live queue table, driven the way a person uses them. Coverage is measured over the shipped code and gated by thresholds in CI. The ticket-lifecycle tests are a named scenario that issues its own ticket.tests/ui/ (14 cases); vitest.config.ts; npm run test:coverage
16Salesforce health probe called the org twice every time Settings opened.LowHeld for 60 seconds. Health a minute old is still health.lib/salesforce.ts
17A malformed response body tripped the circuit breaker.LowOnly a failed connection or a 5xx opens the breaker; an unreadable body is reported as a bad response and the org is not paused.lib/salesforce.ts

Also done in passing: the last non-null assertion in the codebase is gone, the delivery worker checks the ticket still exists before building a payload, and the three timers in the workspace shell (heartbeat, toast, QR link) moved into one hook so the shell reads as layout and state.

4. Decisions kept on purpose, and why

A reviewer who disagrees with any of these should find the argument here, not have to reconstruct it.

DecisionWhat a stricter reading wantsWhy it stands
The application role may call every function, including retention and the routing tickReserve maintenance functions for the owner or a third roleThe scheduler runs as the same role by design, and it is the process that needs those two functions. A third credential for two functions adds a secret to rotate and a failure mode for a gain that only matters if the web role is compromised, in which case the attacker already holds every ticket. Revisit if the scheduler ever gets its own role.
Three stylesheets remainOne styling systemMeasured: 202 of 623 selectors are defined in more than one file. The 91 blocks that were provably dead are gone. The remaining 230 overlaps change what the customer sees if touched, so they are a design decision to be made with a designer and a screen, not a code change to be made blind before a demonstration.
Validation does not key on NODE_ENVRefuse an http origin in productionThe first version did exactly that, and refused to start on a laptop, because the production build is the same artefact everywhere. The rule that actually protects users is that the cookie's Secure flag agrees with the origin's scheme; that is what is enforced. An http origin is allowed and logged as insecure at boot, because policing where a build runs is an operator's decision, not the code's.
Business rules in PostgreSQL, one advisory lock, the API inside Next.js, forward-only migrationsSee the response of 22 September to the first reviewUnchanged and unchallenged by this review. The lock was measured then (96 to 214 ms per tick with 200 to 400 waiting) and measured again after the indexes; see section 3.
Substring search and offset paging on the queueTrigram index and keyset pagingThe queue holds today's tickets, a few dozen rows. Both techniques are ready to hand and become worthwhile when the history is searched, which no screen does yet.
