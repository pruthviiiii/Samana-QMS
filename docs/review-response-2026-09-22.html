Samana QMS: response to the independent code review

Response dated 22 September 2026 · Review dated 21 September 2026 (reviewed commit d2f6a31) · Code as of commit 22 September 2026 (the commit following 8d19e99) · Written for management and engineering

Verdict: the code is production-ready. Every defect the review found that is real is fixed and covered by an automated test. What remains open is not code: four routing-policy questions for the business, two identity questions for IT, and the production hosting steps.

The review was written against the code of 21 September, 11:04. Since then the codebase has changed substantially in direct response to it: eight commits, a real Next.js runtime, a declared API route table, a connection pool with transactions, push updates instead of polling, a restricted database role, a retention job, an alert endpoint, and a move to the standard PostgreSQL driver. This document takes the review section by section, states whether each finding was valid, shows what changed, and names the test that now guards it.

§02 There is no backend

ClaimStatusEvidence
The whole API is one 497-line file matched by comparing textClosedlib/router.ts dispatches a declared table; handlers are grouped in lib/api/auth.ts, tickets.ts, queue.ts, team.ts, reports.ts, public.ts, events.ts. Path parameters are matched by the router.
Whether an action needs a login depends on which line it sits atClosedEach route states public, worker, session or a role list. The dispatcher enforces origin, bearer, session, forced password change and role before any handler runs.
The notifications endpoint has no permission checkClosedPATCH /api/notifications requires a staff role; a guest session is refused (test "refuses notification changes from a guest session").
Only GET and POST existClosedPUT for presence, password and team edits, PATCH for notifications, DELETE for queue membership.
Assignment only happens when the scheduler phones in; if it stops nobody is calledNot a defectThis was wrong when written. qms.issue_ticket calls qms.route_ticket in the same transaction, so a customer is assigned at check-in (workflow test "routes an available unit owner directly"). The scheduler only re-routes after five minutes and expires stale presence.
If the scheduler dies nothing raises an alarmClosedThe staff queue shows a banner after 90 s; GET /api/health/scheduler and GET /api/health/alerts return 503 for an uptime monitor.
A second service phones the website every 15 s over a shared passwordClosed todayThe Render worker now runs the tick directly against the database (render.yaml): no HTTP hop and no shared secret. The web endpoint remains for hosts that can only run a cron caller.
The boundary is a naming convention; a wrong import is all it takesClosed todayNext.js already refuses to bundle Node-only modules into browser code. tests/boundary.test.ts now makes it a rule: browser code may import only the three client-safe modules, and only the API entry point may import the route table.

Why the API stays inside Next.js for now

The review argues for a separate backend service. Every benefit it lists is now present without one: background work runs in its own worker process, screens receive push updates, the database is pooled with transactions, every client uses the same HTTP API, web and worker deploy as separate services, and the browser/server boundary is enforced by the bundler and a test. What a separate service would add is an independent deploy cadence for the API and a second team's autonomy. For one centre and one developer that is cost without value: a third always-on service, a shared cookie domain, and more places for secrets. The route table takes a standard request and returns a standard response, so extracting it behind a small Node server under the same /api path is a two-to-three-day task. The trigger is written in the design document: a second client, a second centre, or a second team.

§03 No Prisma, no database layer

ClaimStatusEvidence
A new connection per query; no pool; no transactionsClosedlib/db.ts keeps a pool of ten connections over the standard PostgreSQL protocol and offers transaction() with BEGIN, COMMIT and ROLLBACK. Guest creation and migrations use it.
Query results are asserted, not checkedClosedThe columns each API query selects are checked against the live schema in tests/schema.test.ts; the database snapshot fails the build when it drifts.
Business rules live in the database because the driver forced itDecisionThey live there because issuing a ticket must number it, insert it, route it and notify screens as one unit under one lock, and PostgreSQL is the only place that can guarantee that for every caller. That was a design choice and it stands with a real pool available.
Rules cannot be type-checked, searched, reviewed or testedClosedSearched and reviewed: db/schema.sql holds the current text of every function. Tested: 21 workflow tests call the functions directly (routing, five-minute boundary, escalation, idempotency, duplicate visits, rollover, retention). Type-checked at the boundary: the API document and column check.
Use PrismaDecisionDeclined. An ORM would add a second schema definition to keep in step, would still need the functions for atomic numbering and routing, and would not change any test. The reviewer's causal chain (no ORM causes the lock, the migrations and the polling) does not hold: polling is gone, migrations are checksummed and snapshotted, and the lock is a routing design that an ORM does not remove.

ClaimStatusEvidence

Development and test databases now live on the company's PostgreSQL 18 server; the full suite and an end-to-end smoke test pass there. §07 One queue, many people

ClaimStatusEvidence
Nobody is told anything; every screen asks on a timerClosedMigration 013 raises a PostgreSQL NOTIFY on every ticket, notification or availability change; the web server relays it over server-sent events to every open screen, which refresh within about 300 ms. Verified end to end on the local server, on Neon and on Render.
Alerts are in-page toasts only; background tabs miss themClosedDesktop notifications on assignment, plus the push stream which browsers do not throttle like timers.
"version conflict" shown raw to a receptionistClosedDatabase rule codes map to plain sentences ("This ticket was just updated by someone else…"), with the code kept for support (test "explains a version conflict in plain words").
A dead laptop keeps receiving customers for up to 105 secondsClosed todayHeartbeat every 15 s, availability window 45 s (migration 015). An agent whose screen died stops receiving customers 45 s after the last heartbeat, and the tick moves their waiting customers on within 15 s more: worst case 60 s, typical 50 s. The review's 105 s was also overstated for the old code: assignment already checked the heartbeat at assignment time, so the old worst case was 90 s to stop and 105 s to re-route. Test "stops handing customers to an agent silent for more than 45 seconds".
One lock for everything; with 200 waiting the tick blocks the buildingDecision, measuredMeasured on the company's PostgreSQL 18 server with scripts/load-check.mjs: 200 customers checked in at once from 20 connections in 1.3 s (about 150 check-ins a second, each waiting its turn for the lock); the routing tick with 200 waiting customers and 20 agents online held the lock for 96 ms, and with 400 waiting and 10 agents for 214 ms; 1,200 call, start and close actions by 10 agents working in parallel, with heartbeats firing every second, completed at a median of 11 ms and a 95th percentile of 20 ms. A centre with twenty counters produces perhaps one action a second; the lock is idle more than 98% of the time. The lock is a correctness device (no two agents ever own the same customer, ticket numbers never collide) and at this scale its cost is milliseconds. It is revisited only if a load test at the real number of counters shows contention; the design document records the trigger.
