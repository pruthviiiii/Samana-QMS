2. Defence of the design decisions

The review does not only report defects; it prefers a different architecture in several places. Those preferences are legitimate, and in each case below the alternative was considered and not taken. This section gives the reason, the evidence, and what it would cost to change course if the business disagrees. Nothing here is defended on taste alone.

2.1 Business rules in PostgreSQL functions rather than an ORM

AspectPositionDetail
ReviewerUse PrismaA single master description of the data catches mistakes before the code runs; rules inside the database cannot be type-checked, debugged, searched or tested.
Our choiceRules stay in PL/pgSQLIssuing a ticket must read a counter, increment it, insert the ticket, route it to an agent and raise a change notification as one indivisible step. Calling a customer must guarantee that no two agents ever hold the same ticket, and that one agent never holds two. Those are database guarantees: one advisory lock and a partial unique index. An ORM does not enforce them; it would move the guarantee into application code, where two web instances race with each other and with the scheduler.
Why it is safe nowThe objections are answeredSearchable and reviewable: db/schema.sql is generated from the live database and holds the current text of every function, so a reviewer reads one file, not eleven migrations. Tested: 21 tests call the functions directly, covering owner-first routing, the exact five-minute boundary, escalation, idempotency, duplicate visits, day rollover, retention and the presence window. Checked: a drift test fails the build if the snapshot and the database disagree, and a second test fails if a column the API selects no longer exists.
Cost to changeAbout two weeks, and a downgradeSix functions would be rewritten in TypeScript with explicit row locking, and every routing invariant retested. The atomicity would then depend on application code being correct in every path rather than on the database. Not recommended.

2.2 One advisory lock for queue writes

AspectPositionDetail
ReviewerThe narrowest possible bottleneckOnly one action in the building can be processed at a time; with 200 people waiting the routing sweep blocks everyone.
Our choiceKeep it, and measure itThe lock is what makes the queue correct: ticket numbers never collide, two agents never take the same customer, and an agent never ends up with two active customers. The review itself concedes the design is safe.
MeasurementMilliseconds, not secondsOn the company's PostgreSQL 18 server: 200 customers checked in simultaneously from 20 connections in 1.3 s; the routing sweep held the lock for 96 ms with 200 waiting and 20 agents online, and 214 ms with 400 waiting and 10 agents; 1,200 call, start and close actions by 10 agents in parallel, with heartbeats firing every second, ran at a median of 11 ms and a 95th percentile of 20 ms. A centre with twenty counters produces roughly one action a second, so the lock is idle the overwhelming majority of the time.
Cost to changeOne day, when evidence demands itSplitting into one lock per service is a contained change plus a re-run of every routing test. The trigger is written down: a load test at the real counter count showing queueing on the lock. scripts/load-check.mjs is in the repository so anyone can repeat the measurement.

2.3 The API inside the Next.js server rather than a separate backend service

AspectPositionDetail
ReviewerA real backend is neededSix benefits are listed: background work, push, a connection pool, one front door for many clients, independent deploys, and a hard security boundary.
Our choiceA modular monolith with a separate workerAll six benefits are present without a third service. Background work runs in its own worker process against the database. Push exists. The pool exists. Every client already uses the same HTTP API. Web and worker deploy as separate services. The boundary is enforced by the bundler and by a test that fails if browser code imports a server module.
What a separate service would addDeploy cadence and team autonomyOnly two things remain: deploying the API without rebuilding the screens, and letting a second team work independently. Neither applies to one centre with one developer, and both cost a third always-on service, a shared cookie domain and another place to keep secrets.
Cost to changeTwo to three days, with a written triggerEach route is a plain request-to-response function in a table, so lifting them behind a small Node server under the same /api path is mechanical. The trigger is recorded in the design document: a second client, a second centre, or a second team.

2.4 Forward-only migrations

The review asks for down migrations. Additive migrations mean the application can be rolled back on its own, which is the rollback that actually gets used; a down migration is written once, rarely exercised, and gives false confidence on the day it matters. The real safety net is a rehearsed restore, which is on the launch list with the exact steps in the operations guide. What was genuinely missing is now in place: every applied file is checksummed so an edited migration is refused rather than silently skipped, and only numbered files are applied. That last point caught a real bug: the runner previously picked up the generated schema.sql and would have failed the production pre-deploy step.

2.5 Smaller decisions the review would have made differently

DecisionReviewer's positionWhy ours standsIf you disagree
Assign the customer at check-in, not when the agent calls One agent can be given ten waiting customers at once The BRD wants the customer to see a counter on the receipt immediately. The exposure is bounded: an uncalled ticket re-routes after five minutes, and since today an agent who disappears stops receiving customers after 45 seconds. A manager can reassign at any time, so the claim that nobody else can pick them up is not correct. Assign at call time, or cap uncalled assignments per agent. One day.
Salesforce token cached for a fixed fifteen minutes The expiry is ignored The client-credentials token response carries no expiry field, so there is nothing to honour. A short fixed cache is the conservative choice, and four token calls an hour are negligible against the org's limits. Nothing to change unless the org starts returning an expiry.
No blanket retry on database queries A network blip fails the query with no second attempt Most writes are not safe to repeat blindly; a retried ticket action could double-apply. Retries exist exactly where they are safe: outbox deliveries with exponential backoff, a Salesforce circuit breaker with a walk-in fallback, pool reconnection, and idempotent ticket issuance keyed on the client's request id. A read-only retry wrapper is half a day if wanted.
Staff accounts are disabled, never deleted Accounts can be switched off but never deleted Audit rows point at the person who acted. Deleting a staff record would break the very trail the review asks for elsewhere. Disabling ends the sessions immediately and is audited. Guest accounts, which reference nothing, are purged after a day. Anonymise a departed member's name after a retention period, alongside the ticket policy.
The QR invite token travels in the address It passes through history and network equipment A QR code can only carry a URL. The token is signed, valid for five minutes, single purpose, and sent over HTTPS, so intermediaries see an encrypted request. It grants a guest session and nothing else. Closed by adding OTP before units are shown, once the SMS gateway exists.
Roles live in the QMS database They come from nowhere official Salesforce has no concept of a QMS queue role, and the BRD gives queue membership to managers inside the app. Single sign-on would change how a person proves who they are, not where the role is stored, so the two are separate decisions. Adopt an identity provider for authentication; roles still map in the app.
