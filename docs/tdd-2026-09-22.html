Section 01

Executive Summary

The Samana QMS issues and routes queue tickets for one Customer Experience Centre. A customer checks in at reception or from their phone by scanning a rotating QR code; the system identifies them against Salesforce, issues a numbered ticket for a service, assigns it to a member of staff, announces it on a waiting-room television, and writes the finished visit back to Salesforce.

The system is three deployables — a Next.js web tier, a standalone API service, and a background scheduler — over one PostgreSQL database. The division is not decorative: the web tier holds no database credential at all, and a repository test fails if a server module is ever imported into browser code. That boundary is the security model, and it is enforced by a test rather than by convention.

The single most consequential decision is that the queue engine lives in the database, as PL/pgSQL functions, rather than in application code. Issuing a ticket is four writes that must commit together; assigning one is a decision that must be made against a consistent view of who is free. Both are transactional problems, and putting them next to the data makes them one transaction rather than a distributed protocol. The cost is real and is stated in §6.6: that logic cannot be unit-tested without a live database, and cannot be stepped through in a debugger. Every mitigation applied to that cost is described in the same section.

3.1 Why three deployables and not one Next.js application

Putting an API inside a web framework is a legitimate arrangement, and it is correct when there is one client, every request is short, nothing runs on a schedule, and nothing is pushed in real time. This system fails all four conditions (§2.1, F1–F4). The specific forces:

ForceWhy a single application cannot satisfy it
Work without a clientRouting must happen when the building is empty of browsers. A request-scoped runtime has nowhere to put that.
Open connectionsA server-sent event stream is a long-lived response held per screen. That is a property of a process, not of a request handler.
Connection poolingTransactions require a session held across statements, which requires a pool that outlives a request.
Credential isolationWith one deployable, the boundary between browser code and the database credential is a naming convention. One wrong import crosses it silently.
Independent releaseA change to a screen should not redeploy the ticketing engine, and the two carry different review standards.
The boundary is enforced, not documented

A split that exists only in folder names decays. tests/boundary.test.ts walks app/ and components/ and fails the build if any file imports a server module, pg, @prisma/* or a node: builtin — and separately asserts that server/handler.ts is the only importer of the route table. The architecture is therefore a property the test suite defends.

3.2 Trust between the tiers

The web tier reaches the API over HTTP. On the available Render plan the API has a public address, so it cannot rely on network isolation and gates itself instead: every forwarded request carries a shared token, and the API refuses anything without it.

server/handler.ts
const READINESS = '/api/health';
async function requireProxyToken(request: Request) {
  const expected = config().API_PROXY_TOKEN;
  if (!expected) return;
  if (new URL(request.url).pathname === READINESS) return;
  const given = request.headers.get('x-internal-token') ?? '';
  if ((await sha256(given)) !== (await sha256(expected)))
    throw new HttpError(401, 'This address serves the web tier only.', 'NOT_VIA_WEB_TIER');
}

The comparison is over digests rather than the raw strings so that it does not leak length or share a timing profile with the secret. The readiness path is exempt because the load balancer must be able to probe it, and it reveals nothing.

Fail closed, by assertion

A missing token would silently open the API. assertApiConfig() therefore refuses to start a production API without either API_PROXY_TOKEN or an explicit API_TRUSTS_NETWORK=true. The check lives on the API's own start path and not in the shared assertConfig() — the scheduler holds no socket and has nothing to protect, and requiring the token there once stopped routing in production. tests/config.test.ts now asserts the scheduler starts without it.

Section 04

Data Layer

4.1 One pool, two access paths

The process opens exactly one connection pool. Prisma runs over that same pool through the pg driver adapter, so a process never holds two independent sets of connections or two TLS configurations.

lib/db.ts · lib/prisma.ts
export function pool() {
  if (!current)
    current = new pg.Pool({
      connectionString: config().DATABASE_URL,
      options: '-c timezone=UTC',   // the engine names Asia/Dubai explicitly
      max: 10,
      idleTimeoutMillis: 30000,
      allowExitOnIdle: true,
      statement_timeout: 15000,
      query_timeout: 20000,
    });
  return current;
}

export function prisma() {
  if (!client) client = new PrismaClient({ adapter: new PrismaPg(pool()) });
  return client;
}

Connections are pinned to UTC rather than left to the server's default, because the Prisma client assumes UTC when it reads timestamps. Calendar-day rules name Asia/Dubai explicitly wherever they appear, so nothing depends on where the database happens to run. Statement and query timeouts are set at the pool so a pathological wait fails rather than hanging a screen.

4.2 Why both Prisma and raw SQL

Prisma is the schema of record and types every ordinary read and write. It cannot express the queue engine: PL/pgSQL functions, triggers, partial indexes and views are outside its language. Rather than degrade the engine to fit the ORM, or abandon typing for the sake of uniformity, the split is explicit and the boundary is validated.

PathUsed forSafety
Prisma clientRecords and relations — staff, sessions, events, notifications, lookups, deliveries, servicesCompile-time types generated from prisma/schema.prisma, which is introspected from the live database.
Validated raw SQLEngine functions, the ticket view, aggregates, and the two statements that must be single atomic writesEvery row parsed against a Zod schema at runtime before use.
lib/data/rows.ts — the boundary
export function rows<T extends z.ZodType>(schema: T, result: unknown[], label: string): z.infer<T>[] {
  return result.map((row, index) => {
    const parsed = schema.safeParse(row);
    if (!parsed.success)
      throw new Error(
        `Unexpected row shape from ${label} (row ${index}): ` +
          parsed.error.issues.map((i) => i.path.join('.') + ' ' + i.message).join('; '),
      );
    return parsed.data;
  });
}
Assertion replaced by check

The earlier design cast query results with as T[] — an assertion the compiler accepts and the runtime never verifies, so a renamed column reached a staff screen as undefined. Now a missing or retyped column throws at the boundary, naming the query and the row. All raw call sites go through rows() or one(); the single remaining cast lives inside query() itself and is what those two functions exist to discipline.

Section 05

Schema Authority & Migrations

5.1 Three descriptions, one truth

The database is described in three places, and the relationship between them is deliberate: the numbered migrations are the only thing that changes a database, and the other two are derived and verified.

ArtifactAuthorityKept honest by
db/0NN_*.sqlSourceApplied in order, each inside one transaction, each checksummed.
db/schema.sqlDerivedtests/schema.test.ts regenerates the snapshot from the migrated database and fails on any difference.
prisma/schema.prismaDerivedIntrospected with npm run prisma:pull; tests/prisma-schema.test.ts fails when it drifts.

This answers the question a reviewer asks first — what does this system do today? — with one file rather than with eleven migrations read in date order.

5.2 Forward-only, and why

The runner records a SHA-256 of each applied file and refuses to run one that has been edited.

scripts/migrate.mjs
if (applied) {
  if (!applied.checksum) { /* record it, first run after the ledger gained the column */ }
  else if (applied.checksum !== checksum)
    throw new Error(
      `${name} was changed after it was applied. Applied migrations are immutable; add a new migration instead.`,
    );
  continue;
}
await db.transaction(async (run) => {
  for (const statement of splitStatements(content)) await run(statement);
  await run('INSERT INTO qms.migrations(name,checksum) VALUES($1,$2)', [name, checksum]);
});

Without the checksum, editing an applied migration to fix a bug produces "Already applied" and the fix silently never runs. That failure is invisible and was worth closing.

Why there are no down migrations

A down migration that has never been executed is a script that does not work, and an incident is the worst moment to discover that. The replacement is a written procedure (docs/rollback.md) built on two properties this design maintains deliberately: a snapshot is taken before every migrating deploy, and each migration keeps the function signatures the previous application version calls. That second property means rolling back the application alone is almost always the correct first move, and it takes a minute. Reverse scripts for the recent migrations are written out in that document, including the one thing 017 cannot restore and why it costs a rotation order rather than any record.

Section 06

The Queue Engine

The engine answers one question repeatedly: who should serve this customer next? It is 22 PL/pgSQL functions in schema qms. This section states the rules and the reasoning; §7 covers how they are serialised.

6.1 Why the engine is in the database

OptionChosenReasoning
Application code, ORM transactionsNoViable, and the conventional answer. Rejected because every assignment decision reads the state of all candidate agents and all their active tickets; doing that in application code means either holding a long transaction across network round trips, or accepting a race. The round trips are the cost that matters: an assignment becomes 5–8 sequential hops instead of one.
Application code, optimistic retryNoRetry loops are correct but make the worst case unbounded and the behaviour hard to reason about under contention — precisely when a reception floor is busy.
PL/pgSQL functionsYesThe decision is made where the data is, inside one transaction, with row locks the planner already understands. Issuing a ticket — read counter, increment, insert, route — is one statement from the application's point of view and one transaction from the database's.

The honest counter-argument is that this is the least visible place to put business rules, and §6.6 addresses it directly rather than dismissing it.

6.3 Fairness is per person, not per counter

The original design kept a rotation cursor per (service, user). A member of staff covering three counters therefore had three independent cursors, and work done at one counted for nothing at the others — so whoever helped in the most places was handed the most customers. Migration 017 replaced it with one cursor on the person.

qms.assign_ticket — migration 017
IF p_user IS NOT NULL THEN
  INSERT INTO qms.notifications(user_id,ticket_id) VALUES(p_user,p_ticket);
  -- One cursor for the person, not one per service: a customer taken at any
  -- counter moves them to the back of every queue they cover.
  UPDATE qms.users SET rotation=nextval('qms.rotation_position') WHERE id=p_user;
END IF;

The cursor is a monotonic sequence rather than a timestamp so that two assignments in the same transaction are still strictly ordered. A new account takes its value from the same sequence on insert, which is why somebody added to a queue joins the back of the rotation instead of jumping to the front — the previous NULLS FIRST ordering gave newcomers priority over everyone who had been working all day.

6.4 One customer at a time

Eligibility previously treated a person as free until they had actually called someone, so ten waiting customers could all carry one agent's name while nobody else could pick them up.

qms.choose_available — current
SELECT u.id FROM qms.users u
 WHERE u.enabled AND u.online AND u.last_seen>now()-qms.presence_window()
   AND u.role=ANY(qms.serving_roles()) AND p_service=ANY(u.services)
   AND (p_exclude IS NULL OR u.id<>p_exclude)
   -- Already holding a customer, whether or not they have called them yet.
   AND NOT EXISTS(SELECT 1 FROM qms.tickets t
                   WHERE t.assigned_to=u.id AND t.status IN ('waiting','called','serving'))
 ORDER BY u.rotation,u.created_at,u.id LIMIT 1
The cost of the cap, and how it is paid

Holding one customer at a time would leave a freed agent idle until the next 15-second tick. Rather than accept that, closing a visit offers that agent the next customer immediately, inside the same transaction as the close:

IF p_action IN ('close','no_show') AND t.assigned_to IS NOT NULL THEN
  PERFORM qms.offer_next(t.assigned_to);
END IF;

qms.offer_next re-checks presence and that the agent now holds nothing, then takes the highest-priority, oldest unassigned ticket among the services they cover. The invariant that an agent has at most one called or serving ticket is additionally enforced by a unique partial index, so it holds even against a code path that forgets:

CREATE UNIQUE INDEX one_active_service_per_agent ON qms.tickets (assigned_to)
  WHERE status = ANY (ARRAY['called','serving']) AND assigned_to IS NOT NULL;

6.5 Service urgency

Migration 017 added qms.services.priority (0–9, admin-settable on the Queues screen). The sweep orders by priority first and arrival second, so a refund can be routed ahead of an older general enquiry — while arrival order still decides inside a service, which is the property customers can see and would rightly object to losing.

SELECT t.id FROM qms.tickets t JOIN qms.services s ON s.id=t.service_id
 WHERE t.status='waiting'
 ORDER BY s.priority DESC,t.created_at,t.id
 LIMIT greatest(p_limit,1) OFFSET greatest(p_offset,0)

Section 07

Concurrency & Locking

7.1 The model

Assignment decisions are serialised by one transaction-scoped advisory lock, pg_advisory_xact_lock(1947301), taken by ticket actions, issuance, queue membership changes, staff record saves and the routing sweep. This is a single-writer model for the assignment critical section.

OptionChosenReasoning
Per-service locksNoLooks like the obvious refinement and is wrong here: a member of staff covers several services, so two services choosing concurrently can pick the same person. The lock would have to cover the candidate set, which is not per service.
Optimistic concurrency onlyNoAlready present for ticket edits via a version column. Insufficient for selection, where the conflict is over a shared resource rather than a single row.
One advisory lock, bounded holdYesMakes double-assignment impossible by construction. At one branch the throughput ceiling is far above demand, and the hold time is the thing to manage — which §7.2 does.

7.2 Bounding the hold rather than removing the lock

The sweep previously took the lock once and looped over every waiting ticket while holding it, so with a long queue no agent anywhere could call, start or close. Two changes fixed the consequence without giving up the guarantee.

First, the sweep routes in bounded batches. Each call is its own transaction, so the lock is released between them and staff actions interleave.

lib/data/functions.ts
const ROUTING_BATCH = 25;
export async function routeDue(): Promise<number> {
  await query('SELECT qms.route_maintenance()');
  let total = 0;
  for (;;) {
    const result = await query('SELECT qms.route_waiting($1,$2) checked', [ROUTING_BATCH, total]);
    const done = one(checkedRow, result, 'route_waiting').checked;
    total += done;
    if (done < ROUTING_BATCH || total >= ROUTING_CEILING) break;
  }
  await query('SELECT qms.note_worker_run($1)', [total]);
  return total;
}

The offset is the count already processed, which is correct because routing a ticket assigns it but leaves it waiting — the result set does not shrink underneath the cursor.

Second, heartbeats left the lock entirely. Every signed-in agent sends one every 15 seconds; at twenty staff that is the highest-frequency writer in the system, and it has no business queueing behind a routing sweep. It now locks only the account row it writes.

qms.set_presence
-- The one account row, not the global lock: every agent sends this every 15
-- seconds and must not queue behind the routing sweep. Routing may therefore
-- read an agent as online in the instant they go offline; the next sweep moves
-- that customer on, which is what already happens for a dead screen.
SELECT online,enabled INTO was,allowed FROM qms.users WHERE id=p_user FOR UPDATE;
Measured, not asserted

At 400 waiting tickets and 20 agents on PostgreSQL 18, the wait to acquire the lock during a sweep fell from p50 252 ms / max 252 ms to p50 18 ms / max 53 ms. Batching costs about 45% more total sweep time (365 ms against 253 ms) for the extra round trips — the intended trade, since the sweep runs on a timer with nobody waiting on it while the agent is a person standing at a counter. Reproduce with node --env-file=.env.test scripts/load-check.mjs 20 400 20.

Known limit

This is a single-writer design for assignment. It is right for one branch and would need revisiting — most likely as a lock per staff pool rather than per service — before a multi-site rollout. That is a deliberate boundary of the current design, not an oversight.

Section 08

Real-Time Delivery

8.1 Why server-sent events over PostgreSQL NOTIFY

OptionChosenReasoning
Polling onlyNoWas the original design. A television showing a called number five seconds late is the product failing at its one visible job, and it put ~2,300 queries a minute on an idle database.
WebSocketsNoBidirectional, and nothing here needs a client→server channel — clients already have a REST API. Costs a second protocol, its own auth handshake and its own proxy behaviour for no gain.
External brokerNoA fourth deployable and a second source of truth for "something changed", when the database already knows.
SSE fed by LISTEN/NOTIFYYesOne direction, plain HTTP, no extra infrastructure, and the signal originates at the only place that can know a change committed — a trigger on the data itself.

8.2 Mechanism

A trigger raises NOTIFY qms_changes when tickets, notifications or staff availability change. One database session per API process holds the LISTEN; every connected screen holds one SSE response.

lib/api/events.ts
send('retry: 5000\n' + frame('status', JSON.stringify({ listening: listening() })));
unsubscribe = subscribe(
  (kind) => send(frame(null, JSON.stringify({ kind }))),
  (ok) => send(frame('status', JSON.stringify({ listening: ok }))),
);
ping = setInterval(() => send(': ping\n\n'), 25000);

The comment ping every 25 seconds keeps intermediaries from closing an idle stream. Headers include X-Accel-Buffering: no so a buffering proxy does not hold frames.

8.3 The stream is advisory; the client stays correct without it

The critical design property is that the stream is an optimisation, never the source of truth. The server reports whether its database listener is actually established, and a screen that is not told so keeps its own faster interval.

components/qms/use-queue.ts
const live = useLive(enabled, () => void refresh(true));
useEffect(() => {
  if (!enabled) return;
  const timer = setInterval(() => void refresh(true), live ? 30000 : 5000);
  return () => clearInterval(timer);
}, [enabled, live, refresh]);
Connected is not the same as listening

A stream can be open while the database session behind it has dropped — the worst case, because the screen believes it is current. The status frame carries listening separately from the connection state, and the client treats only a confirmed listener as live. tests/ui/use-live.test.tsx pins this, along with the burst debounce and that a re-render does not open a second stream.

Deployment dependency

LISTEN needs a session pinned to one server connection. A pooler in transaction mode accepts the command and never delivers a notification — silently. listenUrl() therefore rewrites a Neon -pooler hostname to the direct endpoint for this one connection; behind PgBouncer the same connection must bypass the pool. Getting this wrong degrades to polling rather than breaking, which is why it must be checked deliberately rather than noticed.

Section 09

API Specification

9.1 Routes are data

Every route is a record declaring its method, path, access rule and summary. The dispatcher enforces the declaration before the handler runs, so access never depends on where a handler sits in a file.

lib/router.ts
export type Auth =
  | { kind: 'public' }                        // no session; the handler validates its own inputs
  | { kind: 'worker' }                        // bearer WORKER_SECRET from the scheduler
  | { kind: 'session' }                       // any signed-in account, even before a password change
  | { kind: 'roles'; roles: readonly Role[] }; // signed in, password set, role listed

export interface Route {
  method: Method;
  path: string;            // e.g. 'tickets/:id/action'
  auth: Auth;
  summary: string;         // one line for the generated API document
  handler: (context: Context) => Promise<Response>;
  body?: ZodType;
}
lib/router.ts — dispatch
// Browsers must prove same-origin for every state change; the scheduler is
// server-to-server and proves itself with its own credential instead.
if (request.method !== 'GET' && route.auth.kind !== 'worker') sameOrigin(request);
if (route.auth.kind === 'worker') { /* constant-time bearer comparison */ }
else if (route.auth.kind !== 'public') {
  user = await requireUser(request);
  if (route.auth.kind === 'roles') {
    if (user.must_change_password) throw new HttpError(403, 'Change your temporary password before continuing.');
    if (!route.auth.roles.includes(user.role)) throw new HttpError(403, 'You do not have permission for this action.');
  }
}
Three properties fall out of this shape

The route table is enumerable, so docs/openapi.json is generated rather than maintained and tests/routes.test.ts asserts every route declares a method, path, access rule and summary with no duplicates. Access is a value rather than a control-flow position, so a new route cannot accidentally inherit exemption from one above it. And the role groups it declares access with are the domain's own groups — there is no second list to keep in step.

9.2 Access model in force

AccessCountExamples

9.3 Errors are identified by code, not by prose

Database rules are raised with RAISE EXCEPTION (SQLSTATE P0001) and mapped to a status and a sentence a person at a desk can act on.

lib/errors.ts
export const RULE_MESSAGES: Record<string, [number, string]> = {
  VERSION_CONFLICT: [409, 'This ticket was just updated by someone else. It has been refreshed; please try again.'],
  AGENT_BUSY:       [409, 'That team member is already with a customer.'],
  DUPLICATE_VISIT:  [409, 'This customer already has an open ticket for this service.'],
  LOOKUP_EXPIRED:   [409, 'The customer lookup has expired. Look the customer up again.'],
  // …
};

Identity is a field — HttpError.code and the SQLSTATE — never a substring of a sentence. Rewording a message can therefore never change a status code, and a customer's closing note containing the word FORBIDDEN can never be mistaken for a rule violation. Previously these codes were shown to staff verbatim, lowercased: a receptionist with a customer in front of them read "version conflict".

Section 10

Security Model

10.1 Credentials and sessions

ControlImplementation
Password hashingPBKDF2-SHA256, 600,000 iterations — the current OWASP figure for this algorithm. Each hash carries its own iteration count, and a hash below the current factor is transparently re-hashed at the next successful sign-in.
VerificationConstant-time comparison. An unknown username is verified against a dummy hash of the same work factor, so a wrong username costs the same time as a wrong password.
Session token256 bits from crypto.getRandomValues, stored only as SHA-256. A database read cannot reconstruct a live session.
CookieHttpOnly; SameSite=Strict; Secure (when the origin is https), 8-hour lifetime.
RevocationChanging a password or disabling an account deletes every session for that user in the same transaction as the change.
Database roleThe runtime connects as a restricted qms_app role — DML and EXECUTE in schema qms, no DDL. Migrations use a separate owner string.
lib/security.ts
export const PBKDF2_ITERATIONS = 600000;
export async function verifyPassword(password: string, hash: string) {
  const [algorithm, iterationString, salt] = hash.split('$');
  const iterations = Number(iterationString);
  if (algorithm !== 'pbkdf2' || !salt || !Number.isInteger(iterations) ||
      iterations < 100000 || iterations > 1000000) return false;
  const actual = await hashPassword(password, salt, iterations);
  if (actual.length !== hash.length) return false;
  let diff = 0;
  for (let i = 0; i < actual.length; i++) diff |= actual.charCodeAt(i) ^ hash.charCodeAt(i);
  return diff === 0;
}

10.2 Browser protections

Set in proxy.ts, which runs before every page request. The content security policy is nonce-based with strict-dynamic and no inline allowance, so an injected script is refused by the browser rather than merely discouraged.

const nonce = btoa(crypto.randomUUID());
const policy = [
  "default-src 'self'", "base-uri 'self'", "object-src 'none'",
  "frame-ancestors 'none'", "form-action 'self'",
  `script-src 'self' 'nonce-${nonce}' 'strict-dynamic'${production ? '' : " 'unsafe-eval'"}`,
  "style-src 'self' 'unsafe-inline'",     // React sets style attributes; a style injection cannot execute
  "img-src 'self' data: blob:", "font-src 'self'",
  `connect-src 'self'${production ? '' : ' ws: wss:'}`,
].join('; ');

A fresh nonce per request means pages render per request rather than being statically cached — a deliberate cost accepted for the stronger policy. Typefaces are self-hosted, so font-src 'self' holds without exception.

10.3 Cross-site request forgery

Every non-GET route requires an Origin header exactly matching APP_ORIGIN, combined with a SameSite=Strict cookie. A synchroniser token was considered and not used: with a strictly same-site cookie and a mandatory origin check there is no cross-site path that reaches a handler, and the token would add state to every form for no additional coverage. The scheduler is exempt because it is server-to-server and proves itself with a bearer credential instead.

10.4 Rate limiting

The window is one atomic statement, so two requests arriving together cannot open two windows and spend the budget twice.

INSERT INTO qms.rate_limits(key,window_start,count) VALUES($1,now(),1)
ON CONFLICT(key) DO UPDATE SET
  count = CASE WHEN qms.rate_limits.window_start > now()-make_interval(secs=>$2)
               THEN qms.rate_limits.count+1 ELSE 1 END,
  window_start = CASE WHEN qms.rate_limits.window_start > now()-make_interval(secs=>$2)
                      THEN qms.rate_limits.window_start ELSE now() END
RETURNING count

Sign-in is bounded three ways — globally, per account, and per client address — so neither a single account nor an attacker rotating usernames can drive unbounded password hashing. The client address is trusted only from a header the deployment explicitly names, and the web tier overwrites that header on every forwarded request so a client cannot forge it.

10.5 Data protection

  • Identifier exposure is opt-in. Emirates ID, passport and mobile leave the system only when a manager explicitly requests identifiers=true on an export, and that request is recorded in the activity log with its filters.
  • Spreadsheet safety. Every CSV cell beginning = + - @ or a control character is prefixed with an apostrophe, so an exported note cannot execute as a formula.
  • Logs carry shapes, not values. The request log masks UUID path segments, so a private status token never reaches a log line; failure logs record the error type and SQLSTATE, never the message, which may contain customer data.
  • The customer's phone shows only their own visit. Deliberately reverted from an earlier design that showed surrounding queue positions — the waiting-room television is the board, and other customers' numbers have no reason to be on a stranger's device.
  • Retention is scheduled. qms.apply_retention anonymises identifiers and deletes old events on its own advisory lock, so it cannot block the routing path.
Accepted residual risks

No single sign-on, MFA or HR deprovisioning. A person's role is assigned by an administrator and persists until revoked by hand. This is a product decision, not an oversight, and is the weakest link in a system holding identity documents; it should be the first item in any next phase.

Sign-in is audited without an address or device, so "who used this account, from where" is still unanswerable. The event exists; the attributes do not.

Salesforce Integration

11.1 Surface

The integration user holds API access and class access to three Apex classes and nothing else — no SOQL, no object API. That constraint shapes everything below: the QMS adapts to Salesforce's semantics, never the reverse.

Apex classTriggerPurpose
AccountLookupAPIEvery check-in attemptFind a customer by mobile, Emirates ID or passport; returns units and their calling owners.
QMSUserAPIAdministrator searchOn-demand staff search when adding a team member. Nothing is bulk-imported.

11.2 Resilience — a slow Salesforce must not close reception

The customer lookup is the first step of check-in, so an unreachable Salesforce once meant nobody could be served at all, walk-ins included. Three mechanisms now bound that.

MechanismBehaviour
Walk-in fallbackStaff can issue a ticket without Salesforce. The lookup records degraded: true so the visit is identifiable afterwards.
Circuit breakerThree consecutive transport or 5xx failures pause calls for 30 seconds, so each subsequent check-in fails immediately instead of waiting out a timeout. Exposed on health/alerts as salesforce_paused.
Lookup reuseThe same identifier within two minutes reuses the stored snapshot rather than asking Salesforce again — a retry or a second screen costs nothing.

Delivery back to Salesforce is an outbox with leases rather than an inline call: a trigger writes one row per ticket and kind, the scheduler claims up to ten with FOR UPDATE SKIP LOCKED, and completion is guarded by a lease token so a worker that stalled cannot overwrite a newer attempt. Five failures park a row as failed, which surfaces on health/alerts.

11.3 Customer identity — one phone number, however it was typed

The Apex matches Mobile_Number__c exactly and is not ours to change. Salesforce stores the country code in a separate field, so the value it matches on is the national number. Customers, however, type the same phone four different ways.

lib/domain.ts
export function nationalMobile(value: string): string {
  let digits = value.replace(/\D/g, '');
  if (digits.startsWith('00')) digits = digits.slice(2);
  // Guarded by length: a national number is never itself 971 followed by
  // nothing, and UAE mobiles start 5.
  if (digits.startsWith('971') && digits.length > 9) digits = digits.slice(3);
  if (digits.startsWith('0')) digits = digits.slice(1); // trunk prefix
  if (!/^\d{7,15}$/.test(digits)) throw new Error('Enter a valid mobile number (at least 7 digits).');
  return digits;
}

Normalising strips the country code rather than a fixed number of digits. A "last nine" rule would be correct for the UAE and wrong for the Indian, Afghan and Australian accounts that also exist in the org.

Because the match is exact and the stored data is not uniform, the lookup then offers the shapes the data actually holds, stopping at the first account found:

lib/salesforce.ts
export function mobileVariants(national: string): string[] {
  const seen = new Set<string>();
  const add = (v: string) => { if (/^\d{7,15}$/.test(v)) seen.add(v); };
  add(national); add('0' + national); add('971' + national);
  if (national.length > 10) { add(national.slice(-10)); add(national.slice(-9)); }
  return [...seen];
}
Only a miss advances the loop

An empty result tries the next candidate; anything thrown — a timeout, a 5xx, an open breaker — propagates immediately. A Salesforce that is merely slow therefore still costs one request rather than five, and reception reaches the walk-in path as quickly as before. Verified against the POD2 sandbox: every way of writing one real customer's number reached the same account, each on the first candidate.

A useful side effect: because the stored lookup identifier is normalised, the same person checking in twice is recognised as a duplicate visit rather than two strangers.

Section 12

Performance & Load

12.1 Read paths that grow with history

Two aggregates run on every staff screen refresh. Both scanned the entire ticket table — free at a few hundred rows and linear in the whole archive at a year's volume, which is the shape of problem that is invisible in testing and arrives all at once.

The fix is to say which rows are needed. Active-status counts and today's counts are read through two indexes and combined; the predicate is an OR rather than a date window because a ticket left serving across midnight is still active and must keep counting.

FROM qms.tickets
WHERE ($1::uuid IS NULL OR assigned_to=$1)
  AND (status IN ('waiting','called','serving') OR day=(now() AT TIME ZONE 'Asia/Dubai')::date)
CREATE INDEX tickets_active ON qms.tickets (status)
  WHERE status IN ('waiting','called','serving');
CREATE INDEX tickets_customer_name_trgm ON qms.tickets USING gin (customer_name gin_trgm_ops);

Together that removes roughly 450 ms of pure scan from every staff screen refresh at a year's volume. Reproduce with node --env-file=.env.test scripts/read-path-check.mjs; a sequential scan in its AFTER rows is a regression.

Run ANALYZE after a restore

On a freshly migrated or restored database with no planner statistics, the same sweep measured four times slower and the new indexes were ignored. This is a restore-procedure step, not a tuning suggestion.

12.2 Idle load

With the event stream live a staff screen polls every 30 seconds rather than every five, and the reception television the same rather than every three. The remaining floor is the 15-second presence heartbeat, which is a deliberate trade: it is what lets the system notice a dead screen within 45 seconds, and since migration 017 it no longer touches the global lock.

14.2 Assertions are verified to be able to fail

A guard test that cannot go red is worse than no test, because it is believed. Each new invariant in this baseline was checked by deliberately breaking the behaviour and confirming the specific test failed — the presence-window drift guard, the customer's phone showing no other ticket numbers, the television distinguishing an expired sign-in from a network fault, the empty board drawing no headings, and the scheduler starting without the API gate.

Where coverage is thin, and why it is stated

47% is a blended figure and the distribution matters more than the number: the API and data layers sit between 58% and 100%, while several workspace screens remain at zero. The thresholds in vitest.config.ts are ratcheted to just below the current figure so coverage cannot silently fall, but the honest position is that the staff workspace is the least-tested area of the system.

14.3 Continuous integration

Every pull request runs typecheck, lint, both test projects, npm audit --audit-level=high, and all three builds; a second job starts a PostgreSQL 18 container, migrates it from 001 and runs the full suite with coverage thresholds. Migrating from scratch on every run is what proves the migration path a new environment will take.

Section 15

Deployment & Rollback

15.1 Topology

ServiceStartNotes
samana-qmsdist-node/standalone/server.jsWeb tier. Refuses to boot without API_URL, so a misconfigured deploy fails rather than serving a broken app.
samana-qms-apidist-api/api.mjsRuns migrations as its pre-deploy command, then serves. Refuses to boot in production without a gate.
samana-qms-schedulerdist-worker/worker.mjsConnects to the database directly — no HTTP hop, no shared secret with the API.

15.2 Deployment order and the window it creates

Migrations run in the API service's pre-deploy step, so for a short window the new schema is live under the old application. That window is safe by design and not by luck: every migration keeps the function signatures the previous version calls, and the application never queries the tables the engine owns directly. During the 017 release the old code ran against the new schema for roughly ninety seconds with no error.

Verify the build, not the health check

Health endpoints return 200 throughout a deploy because the old build is still serving. Confirming a release therefore means probing something only the new build has — a new route answering 403 instead of 404, or a new CSS rule present in the served stylesheet — not the absence of alarms.

15.3 Rollback

Full procedure in docs/rollback.md. The decision order is what matters:

SituationAction
Schema applied, application misbehavingRoll back the application. Takes a minute and is almost always right, because migrations preserve the previous version's contract.
A migration added something unwantedApply the written reverse script, then a new migration recording the change.
Data destroyed or corruptedRestore the snapshot. Nothing else recovers it.
Snapshots, not point-in-time

The managed database retains only six hours of point-in-time history — shorter than the time a data problem usually takes to notice. A snapshot taken immediately before a migrating deploy is the real restore point, and taking one is a required step rather than a precaution.
